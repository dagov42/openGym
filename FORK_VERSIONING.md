# Схема версий форка

Статус: принято 2026-11-16, вариант A. Новые теги форка — `fork-vX.Y.Z`; текущий `v1.4.7`
перетегирован в `fork-v1.4.7`. Новых тегов `vX.Y.Z` форк больше не создаёт.

> Обновление 2026-11-17: владелец форка вернул имена без `fork-`. Новые теги и релизы снова
> называются `vX.Y.Z` (и `vX.Y.Z.N` для патч-ревизии), без `(fork)` в названии. iOS
> `MARKETING_VERSION` и Garmin `version` остаются трёхчастными: их форматы не принимают
> четвёртое число, поэтому release-check показывает для них warning. Android `versionName` и
> `package.json` несут полный `X.Y.Z.N`.

## Почему это нужно

- Upstream публикует теги `vX.Y.Z`. Форк уже использовал `v1.4.0`…`v1.4.6`, а `v1.4.7` уже
  запушен. Когда upstream выпустит свой `v1.4.6`, в форке появится конфликт имён: Git не может
  держать два тега `v1.4.6`, указывающих на разные коммиты, а `git fetch --tags` начнёт спотыкаться.
- `v1.4.6` форка уже опубликован с APK (15.11.2026) и красным `tests-ok`; переиздать ту же версию
  нельзя: установленные 1.4.6 не увидят обновление, а APK с тем же `versionCode` не встанет сверху.
- Маркетинговая версия обязана быть простым `X.Y.Z`:
  - iOS `CFBundleShortVersionString` — до трёх чисел, без суффиксов;
  - Garmin Connect IQ `version` — числовая;
  - `compareSemver` в `frontend/src/lib/update.js` читает три числа, суффикс ломает сравнение.
- `versionCode` Android и `CURRENT_PROJECT_VERSION` iOS должны только расти; иначе стор и установка
  поверх старой сборки не примут файл.
- In-app updater читает `tag_name` релиза и сейчас срезает только `^v`. Тег `fork-v1.4.7` без
  правки кода он не поймёт.

## Схема

### 1. Два пространства тегов

| Кто | Тег | Пример |
|---|---|---|
| Upstream | `vX.Y.Z` | `v1.4.6` |
| Форк, всё новое | `fork-vX.Y.Z` | `fork-v1.4.7` |

- `v1.4.0`…`v1.4.7` форка остаются как legacy. Новые теги `vX.Y.Z` форк больше не создаёт.
- Upstream-теги не тянем в то же пространство имён: см. «Коллизии» ниже.

### 2. Маркетинговая версия (её видят стор, updater и пользователь)

Всегда простой `X.Y.Z`, всегда **строго больше** версии upstream, которую содержит релиз, и больше
любой версии, уже использованной форком или upstream.

Правило выбора:

```
next = max(upstream_version_included, last_fork_version) + 1 patch
```

Minor/major — только когда масштаб изменения это оправдывает (как у upstream). Пример:

| Событие | Версия форка |
|---|---|
| База upstream 1.4.5, первый релиз форка | 1.4.6 |
| Исправление после красного релиза 1.4.6 | 1.4.7 |
| Смержен upstream 1.4.6 | 1.4.8 |
| Upstream позже выпустил 1.4.8 | 1.4.9 |

Почему так: форк всегда на шаг впереди upstream-релиза, который он содержит. Это единственное, что
заставляет in-app updater предложить обновление. Если upstream догоняет тот же номер — форк просто
делает следующий патч.

Проверка перед релизом:

```bash
git tag --list 'v*' 'fork-v*' --sort=-v:refname | head
```

и секции `## vX.Y.Z` в `CHANGELOG.md`. Использованную версию не переиспользуем никогда.

### 3. Имена релиза и артефактов

- Git-тег: `fork-vX.Y.Z`.
- Название GitHub release: `vX.Y.Z (fork)`.
- APK/AAB: `openGym-X.Y.Z.apk`, `openGym-Plus-X.Y.Z.apk`, `openGym-HD-X.Y.Z.apk`,
  `openGym-Offline-X.Y.Z.apk`, `openGym-X.Y.Z.aab` — без префикса `fork-`.
- Docker: `X.Y.Z`, `X.Y`, `latest` — из тега срезается `fork-v`.
- Release notes: секция `## vX.Y.Z` из `CHANGELOG.md`, слово в слово.

### 4. Build numbers

| Где | Правило |
|---|---|
| Android `versionCode` | строго +1 к предыдущему публичному релизу; не переиспользуется |
| iOS `CURRENT_PROJECT_VERSION` | строго +1 к каждой загрузке в App Store Connect |
| iOS `MARKETING_VERSION` | `X.Y.Z` |
| Garmin `manifest.xml version` | `X.Y.Z`, каждая загрузка выше предыдущей |

Исправленный релиз — это **новый патч** (`X.Y.(Z+1)`) с новыми `versionCode`/build, а не та же
версия с пересобранным APK.

### 5. Исправленные релизы

- Опубликованный тег и релиз не двигаем и не перезаписываем.
- Если релиз вышел с красным `tests-ok`, в notes следующего патча пишем, что он исправляет, и
  выпускаем патч. `v1.4.7` — ровно такой случай для `v1.4.6`.
- Удалять ассеты опубликованного релиза можно только по security/legal причине; тогда это
  отдельное решение и запись в журнале.

### 6. Коллизии с upstream-тегами

В форке уже есть `v1.4.6` (опубликован) и `v1.4.7` (тег без релиза). Upstream-теги с теми же
именами нельзя тянуть в `refs/tags/v*`.

- Тянем upstream по веткам: `git fetch origin main release-1.4.6` (или конкретный коммит).
- Если нужен именно upstream-тег, кладём его под другим ref:
  ```bash
  git fetch origin refs/tags/v1.4.6:refs/tags/upstream/v1.4.6
  ```
- Не используем `git fetch --tags origin` в форке; при необходимости `--no-tags`.
- В журнале и release notes ссылаемся на upstream PR/issue и коммит, а не на конфликтующий тег.

### 7. Pre-release и RC

Публичных версий с суффиксом (`-rc.1`, `-fork.2`) нет: их не примут iOS/Garmin, а updater
сравнивает только три числа. Для проверки:

- `ci-*` ветка для `tests-ok`;
- draft GitHub release для сборки и `release-assets-check`;
- публикация только после зелёных `tests-ok`, Release check и asset check.

### 8. Порядок выпуска

1. Версии и секция `## vX.Y.Z` в `CHANGELOG.md`.
2. `node scripts/ci/release-check.mjs fork-vX.Y.Z` — локально зелёный.
3. Push коммита в `main` (или `ci-*` на том же коммите) → `tests-ok` зелёный.
4. Тег `fork-vX.Y.Z` на проверенный коммит → Release check зелёный.
5. Сборка APK/AAB на release-машине; draft release; `upload-release.sh`; `release-assets-check` ok.
6. Публикация релиза. Только после этого in-app updater увидит версию.
7. Docker images публикуются workflow по событию `release: published`.

## Что поправить в коде и CI

- `scripts/ci/release-check.mjs` — срезать `fork-v` и `v`; регэксп секции CHANGELOG оставить
  `## vX.Y.Z`.
- `.github/workflows/release-check.yml` — триггер тегов `['v*', 'fork-v*']`; передавать тег в
  скрипт; проверка «коммит на main» остаётся.
- `frontend/src/lib/update.js` — `tag_name` срезать `^(?:fork-)?v`; тесты на оба вида;
  `RELEASES_PAGE` не меняется.
- `scripts/ci/release-assets-check.mjs` — та же нормализация тега; имена ассетов без `fork-`.
- `scripts/android/upload-release.sh` — `VER=${TAG#fork-v}` с fallback на `${TAG#v}`.
- `.github/workflows/docker-publish.yml` — `VERSION` из тега без `fork-v`; `type=semver` не
  понимает `fork-v`, поэтому теги `X.Y.Z`/`X.Y`/`latest` задать явно (`type=match` или raw).
- `mirror.yml`, `release-assets.yml` — проверить, что тег только передаётся, а не парсится.
- Тесты: `release-check` на `fork-v1.4.7`, `compareSemver`/updater на `fork-v1.4.7`,
  `upload-release.sh` на обоих префиксах.

## Миграция текущего `v1.4.7`

Принят вариант A. Tooling научили понимать `fork-v`, тег `v1.4.7` удалён, `fork-v1.4.7` создан на
проверенном коммите с версиями 1.4.7. GitHub release и ассеты ещё не созданы; до их публикации
in-app updater версию не видит.

Опубликованный `v1.4.6` не переименовываем: это сломает ссылки и уже установленные сборки.
Он остаётся как есть и помечается в notes как заменённый `v1.4.7`.

## Правила, если сомневаешься

- Сомневаешься — поднимай патч.
- Никогда не переиспользуй версию.
- Никогда не публикуй без зелёного `tests-ok` и `release-assets-check`.
- Опубликованный тег не двигаем; исправление — следующий патч.
